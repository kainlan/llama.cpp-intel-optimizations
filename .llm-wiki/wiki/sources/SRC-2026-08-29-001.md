# sycl-perf-baselines.md

## Summary

This source documents SYCL performance baselines for a local llama.cpp fork on Intel Arc GPUs, after the 2026-07-24 hardware change in which an Arc B580 was physically replaced by an Arc Pro B70 (an Arc Pro B50 is the second card). Decision-critical regression guardrails live in CLAUDE.md; this file holds the fuller context and measurement provenance. Since 2026-08-21, every benchmark or correctness-gate run must go through scripts/bench-guard.sh rather than the raw binary: it exits 3 on a corrupted host, otherwise stamps the archived --log with a VALID/SUSPECT verdict as its first line, and applies three preflight refusal classes — any live llama-cli/llama-bench/llama-completion tenant, Shmem >10 GB in /proc/meminfo (the TTM-shmem OOM signature), and PL2 throttling (throttle/status != 0 or act_freq != 0, polled up to 360 s, with the card derived live from PCI device symlinks, never a static cardN). A log not starting with `# bench-guard: VALID` is not a citable baseline. Documented evidence: PL2 throttling alone decayed identical-binary readings 2–5× (HEAD pp512 121.2 → 22.9; baseline-worktree 908.9 → 456), and two 16-hour-stale hung llama-cli tenants depressed every co-resident reading and masked a real B70 defect (llama.cpp-o3h1).

Measurement discipline, each rule paid for by a round of discarded measurements: every figure is mean ± sd across ≥5 separate processes (never llama-bench's within-process ±), free VRAM is recorded on every run (~32.6 GB B70 / ~16.2 GB B50; a background ComfyUI once held 18.3 GiB and invalidated a round), runs key off ONEAPI_DEVICE_SELECTOR rather than the logged device=N, GT resets are checked before and after, A/B arms are interleaved (a blocked design once flipped the same flag's effect from +2.3% to −3.6%), and B70 runs need GGML_SYCL_OP_TIMEOUT_MS=180000. The current certified GPT-OSS 20B MXFP4 default is the oneDNN-batched MoE PP arm (GGML_SYCL_MOE_PP_ONEDNN_F16_BATCHED), made default on both cards by owner ruling llama.cpp-iikr (2026-08-25): B50 871.43 ± 15.59 PP512 / 33.68 ± 0.16 TG128 and B70 1730.68 ± 31.40 / 40.85 ± 1.15, certified clean-host. The earlier A–D tables (old non-batched default: 1414.62 / 893.77 PP512) are declared KNOWN-STALE — they were measured with codescout's OpenVINO embedder secretly resident on the B50, and the old arm collapses to ~130 / ~515 PP512 on a genuinely clean host — with the collapse tracked separately as llama.cpp-9klr (P2, open); the 2026-08-22 policy-route WOQ snapshot (750.36 / 426.80) is demoted to snapshot rows, not gates. Mistral 7B Q4_0 baselines — B70 2495.42 ± 62.88 PP512 / 107.66 ± 1.06 TG128, B50 1187.83 ± 18.79 / 46.53 ± 0.19 — reproduce historical B50 values, localising the GPT-OSS regression to that path rather than the card or driver; all 8 correctness gates (Mistral deterministic completion "1, 2, …, 10", GPT-OSS count gate "1, 2, 3, 4, 5", both devices, both configurations) pass with identical generated text between default and FORCE_LEGACY arms.

Two deep dives round out the document. First, the production batch=1 quantized token-generation path is MMVQ with q8_1 activations, not coalesced DMMV: the TG fast-path in ggml_sycl_mul_mat() returns before both GGML_SYCL_FORCE_DMMV consultation sites, so forcing DMMV at batch=1 requires GGML_SYCL_TG_FAST=0, and the coalesced DMMV kernel is a fallback/debug path. MMVQ's q8_1 activation arithmetic (8 bits per 32-element block, scale amax/127, per-block fp16 sum, matching the upstream CUDA convention) is correct by design, so the historical "12–31% wrong answer" was the right kernel scored against a full-precision oracle; accuracy claims should be read as oracle fit ratios (tests/test-dmmv-q4-0-coalesced.cpp requires the dfloat oracle to fit ≥100× better, cleared by 4239–8150×), and GGML_SYCL_MUL_MAT_ROUTE_TRACE=1 names the kernel actually dispatched. Second, the earlier +21.8% tg128 claim for GGML_SYCL_UNIFIED_FORCE_LEGACY on the B70 does not replicate: an interleaved 6-pair A/B gives +2.3% (t = 0.72, ns) with equal sds on both arms, and on the B50 the flag does nothing. The flag is presence-tested rather than value-tested (so =0 ENABLES the bypass, and the static variable latches per process), it is a no-op on GPT-OSS (whose MUL_MAT already routes backend=legacy by default), but on Mistral it costs ~⅔ of prompt processing (−66.5% B70, −69.9% B50) by diverting the unified/oneDNN route to legacy — "same flag, opposite consequences."

## Key Takeaways

- Every benchmark or correctness-gate run must go through scripts/bench-guard.sh; a log not starting with `# bench-guard: VALID` is not a baseline and must not be cited — cite the SUSPECT reason or re-run.
- bench-guard refuses (exit 3) on stale GPU tenants (live llama-cli/llama-bench/llama-completion), Shmem >10 GB in /proc/meminfo (TTM-shmem OOM signature), and PL2 throttle/act_freq, with the card derived live from the PCI device symlink (0000:03:00.0 B70, 0000:07:00.0 B50) rather than a static cardN index.
- The Arc B580 was physically replaced by an Arc Pro B70 on 2026-07-24; all B580 figures are SUPERSEDED history, and measuring a B70 against a B580 target makes a healthy run look like a catastrophic regression.
- Baseline discipline: mean ± sd across ≥5 separate processes (never llama-bench's single-line ±), record free VRAM on every run (~32.6 GB B70 / ~16.2 GB B50), key off ONEAPI_DEVICE_SELECTOR, check for GT resets before/after, interleave A/B arms, and set GGML_SYCL_OP_TIMEOUT_MS=180000 on B70.
- A blocked design can invert an effect's sign: the same flag measured −3.6% in sequential blocks but +2.3% (t = 0.72, ns) interleaved — blocked output is not a measurement of the flag at all.
- Per owner ruling llama.cpp-iikr (2026-08-25), the oneDNN-batched MoE PP arm (GGML_SYCL_MOE_PP_ONEDNN_F16_BATCHED) is the certified default on both cards: GPT-OSS 20B MXFP4 B50 871.43 ± 15.59 PP512 / 33.68 ± 0.16 TG128, B70 1730.68 ± 31.40 / 40.85 ± 1.15.
- The A–D GPT-OSS tables (1414.62 / 893.77 PP512, old non-batched default) are KNOWN-STALE — measured with codescout's OpenVINO embedder secretly resident on the B50 — and the clean-host collapse of the old default (~130 / ~515 PP512, a 6.7× regression) is tracked as llama.cpp-9klr (P2, open), not fixed by the batched-arm flip.
- Mistral 7B Q4_0 baselines (B70 2495.42 PP512 / 107.66 TG128; B50 1187.83 / 46.53) reproduce historical B50 values, localising the GPT-OSS regression to that path; 8/8 correctness gates pass with identical generated text between default and FORCE_LEGACY arms.
- The production batch=1 quantized TG path is MMVQ with q8_1 activations via the ggml_sycl_mul_mat() TG fast-path; GGML_SYCL_FORCE_DMMV is never read on that path (pair with GGML_SYCL_TG_FAST=0), and the Q4_0 coalesced DMMV kernel is a fallback/debug path.
- The historical '12–31% wrong answer' for Q4_0 coalesced DMMV was the right kernel scored against a full-precision oracle; read batch=1 quantized-dispatch accuracy as oracle fit ratios, never tolerances (the dfloat oracle must fit ≥100× better than the q8_1 oracle).
- GGML_SYCL_UNIFIED_FORCE_LEGACY: the earlier +21.8% tg128 claim does not replicate (+2.3%, ns, interleaved); the flag is presence-tested, so =0 ENABLES the bypass, and it latches per process as a static.
- On GPT-OSS the FORCE_LEGACY flag is a no-op (MUL_MAT already routes backend=legacy), but on Mistral it costs ~⅔ of prompt processing (−66.5% B70, −69.9% B50) by diverting the unified/oneDNN route to legacy — its cost depends entirely on which routing decision the model would otherwise make.

## Contradictions

⚠️ **Contradiction**: An earlier task reported GGML_SYCL_UNIFIED_FORCE_LEGACY worth +21.8% tg128 on the B70 (37.27 ± 2.70 → 45.41 ± 0.30, sequential blocks) with a variance collapse (sd 0.30 vs 2.70); this fork's interleaved A/B gives +2.3% (t = 0.72, ns) with equal sds (2.19 both arms) — the earlier result does not replicate.
⚠️ **Contradiction**: The A–D GPT-OSS tables were previously treated as baselines but are declared KNOWN-STALE: they were measured with codescout's OpenVINO embedder secretly resident on the B50, and the old non-batched default collapses to ~130 / ~515 PP512 on a clean host, a 6.7× regression from the ~894 / ~1415 the tables show.
⚠️ **Contradiction**: The historical '12–31% wrong answer' for the Q4_0 coalesced DMMV path is reinterpreted: it was correct q8_1-MMVQ arithmetic scored against a full-precision oracle, not a kernel defect (0 errors against the q8_1 oracle it actually implements).
⚠️ **Contradiction**: The same flag, build, card, and day produced −3.6% tg128 in sequential blocks but +2.3% in interleaved pairs; the document rules that neither number is the 'real' one and that a blocked design's output is not a measurement of the flag at all.
⚠️ **Contradiction**: An older note claimed the Mistral gate output must end '…14, 15'; that string is unreachable at -n 15 and turned a passing gate into a false alarm (corrected in CLAUDE.md). Likewise the 2026-08-22 policy-route WOQ snapshot rows (~half of baselines) are declared superseded by the 2026-08-25 certified rows.
⚠️ **Contradiction**: B580-era Mistral guardrails (>2000 PP512, >85 TG128) were retired for the card change, yet the B70 clears them comfortably (~2495 / ~108), showing the hardware change was an upgrade on that workload while old-card guardrails remain the wrong gate for a different card.
