# sycl-memory-design.md

## Summary

This document is the narrative onboarding for the key design constraint of a llama.cpp fork's SYCL backend: every GPU, host-pinned, staging, scratch, graph-temporary, KV, oneDNN, and weight-layout allocation flows through one allocator (the unified cache, `ggml_sycl::unified_cache`) and is owned by one lifetime token (`mem_handle`). No backend code calls `sycl::malloc_device`/`malloc_host`/`free` directly, keys anything by a raw device pointer, or stores a raw `void*` as the source of truth. The governing invariant: the cache owns placement, the handle owns lifetime, and a raw pointer is only a transient view resolved from a handle for one immediate use. The authoritative, enforceable version is `docs/design/sycl-canonical-memory-architecture.md`; code lives in `ggml/src/ggml-sycl/{unified-cache,mem-handle}.{hpp,cpp}`.

The design reduces to three primitives: a Planner (`compute_placement_plan`) that is the sole authority for where memory lives, decided once at model load (dense weights fill VRAM before MoE experts); the unified cache, the sole allocator/owner holding the tiered weight cache (VRAM/pinned host/mmap, LRU eviction), VRAM arena with zones, pinned pool, and runtime/KV/scratch allocations under a budget of `min(total*pct, free_at_init)`; and `mem_handle`, a lightweight copyable ref-counted token that resolves lazily and guarantees the backing allocation cannot be freed or evicted while held. Owner rulings dated 2026-08-16 fix two further invariants: "placement decides the executor" (inference executes each op where its data already is — host-resident data runs on CPU, so GPU zero-copy reads of host memory and per-dispatch weight streaming are both forbidden; measured CPU AOS 18–30 GB/s vs GPU zero-copy 11.3 GB/s, ~9.7 µs cross-device latency for CPU expert dispatch via `CpuExpertPool`), and "layout follows residency" (each weight is materialized in the optimal layout for the specific processor that executes on it, per device — B50 vs B70 differ in tile shapes and XMX generation; the route layout must match the materialized layout, as the 2026-08-16 MMID NaN family was caused by routes advertising SOA over AOS bytes).

Allocation goes through one entry point, `unified_allocate(req)`, which routes by `alloc_intent` into a tier (DEVICE_VRAM / pinned host) and a VRAM zone (KV, WEIGHT, ONEDNN, RUNTIME, SCRATCH) and returns a `mem_handle` whose destructor reclaims the allocation; the only sanctioned exception is `ensure_cached_alloc()`, a deliberately out-of-arena, budget-gated path with zero production callers (34 call sites, all under `tests/`), whose conformance is auditable by grep. The dominant shape is owner-first allocation via `unified_allocate_owner()` (48 call sites at `0b7b49e07`), which allocates the intrusive `alloc_owner_control` before the physical allocation so an allocation can never exist without an owner, adding move-only ownership, coordinator-mediated release that can be refused and retried without allocating, and typed failure results. Weights are handed out as WEIGHT-kind handles keyed by `ggml_sycl_cache_id` (tensor identity, not pointer), with lazy generation-counter resolution that lets the cache migrate weights VRAM↔host transparently, and eviction restricted to entries with `in_use_count == 0`. Buffer-scoped weight provenance (merged with the `llama.cpp-f8ws` lane) adds a second minting occasion — owner ids minted at buffer allocation, top-bit namespaced, consumed at `init_tensor`, dropped at buffer free via stored cache ids — alongside a non-owning storage-handle route that slices the buffer's `managed_handle` per MoE expert transactionally and is consulted by the expert resolver before any cache key is formed. The document closes with epoch-refcounted transient zones (llama.cpp-2757 / iiff Option C): rather than the infeasible blanket deletion of bulk zone resets, each reset-only zone gets a ring of equal-sized regions with a per-region live-handle counter that rewinds on zero — though the source text is truncated mid-sentence in that final section.

## Key Takeaways

- Core constraint: every SYCL backend allocation flows through the unified cache and is owned by a mem_handle; no direct sycl::malloc/free calls, no raw-pointer table keys, no stored raw pointers — the cache owns placement, the handle owns lifetime, a raw pointer is only a transient view.
- Three primitives: Planner (compute_placement_plan → placement_plan, sole authority for where memory lives, decided once at load — dense weights fill VRAM before MoE experts), unified cache (sole allocator/owner; tiered weight cache with LRU eviction, VRAM arena + zones, pinned pool; budget = min(total*pct, free_at_init)), mem_handle (lightweight copyable ref-counted lifetime token).
- Placement decides the executor (owner ruling 2026-08-16): data is executed where it already is — GPU VRAM operand → that GPU runs the op; host-pinned operand → CPU runs the op. GPU 'zero-copy' reads of host memory (measured 11.3 GB/s vs CPU AOS 18–30 GB/s) and per-dispatch weight streaming are both forbidden; the fix for VRAM-starved configs is placement (budget, eviction priority), never a streaming path.
- Layout follows residency (owner ruling 2026-08-16): weights are materialized in the optimal layout for the specific device that executes on them (per-device, since B50/B70 differ in tile shapes and XMX generation); the route layout must follow the materialized layout — the MMID NaN family (llama.cpp-mn70/zoly/nkfc) was exactly this drift; 'fall back to AOS' is a correctness stopgap, not the design.
- unified_allocate(req) is the single allocation entry point, routing by alloc_intent to a tier and a VRAM zone (KV/WEIGHT/ONEDNN/RUNTIME/SCRATCH) and returning a mem_handle; the only sanctioned exception is ensure_cached_alloc(), test-only with zero production callers, auditable by a grep that must return exactly two lines.
- Owner-first allocation (unified_allocate_owner) allocates the intrusive alloc_owner_control before the physical allocation so an allocation can never exist without an owner; it is now the dominant shape (48 call sites at 0b7b49e07) and adds move-only ownership, coordinator-mediated releasable-with-refusal (retry allocates nothing), and typed errors.
- Weights are WEIGHT-kind handles keyed by ggml_sycl_cache_id (tensor identity, not pointer): lazy resolution via a global generation counter (~3 ns compare-and-return), re-resolution on staleness for transparent VRAM↔host migration, and eviction allowed only for entries with in_use_count == 0 — if eviction is blocked by leases, that's a missing release to fix, never force eviction.
- Buffer-scoped weight provenance (llama.cpp-f8ws, 2026-08-15) adds a second minting occasion at buffer allocation: owner id seeded from the buffer's managed_meta.id, top-bit (1ull<<63) namespaced so it is disjoint from model Registry ids, stamped at init_tensor, dropped at buffer free via stored cache ids without dereferencing tensors; a non-owning storage-handle route slices the buffer's managed_handle per expert transactionally and is consulted by the expert resolver before any cache key is formed.
- Do/don't rules: never store raw pointers from the cache; key tables on stable_identity_hash, not addresses; keep handles alive until queued work / command graph completes; never add forced eviction, forced reap, or zone reset for memory with live handles (that signals a leaked reference or stale owner).
- Epoch-refcounted transient zones (llama.cpp-2757 / iiff Option C): the llama.cpp-37ba audit showed the blanket deletion of bulk zone resets is infeasible because for reset-only zones (VRAM scratch bump pool, host SCRATCH/STAGING, oneDNN scratch) the bulk reset is the only reclaim path; the design keeps the bump allocator but gives each zone a ring of equal-sized regions with a per-region live-handle counter (epoch) that rewinds on zero — with each region sized at the caller's full requested capacity, not a fraction, to preserve the existing sizing contract. (Source truncated mid-sentence in this final section.)

> The cache owns placement. The handle owns lifetime. A raw pointer is only a transient view, resolved from a handle for one immediate use (a kernel submit, a oneDNN call, a scoped CPU access) and never stored. — SYCL Backend Memory Design (unified cache + mem_handle)

> The planning pass decides where data lives. Inference then executes each op where its data already is. — Owner ruling, 2026-08-16 (placement decides the executor)

> dense weights fill VRAM first, before MoE experts are placed there — SYCL Backend Memory Design (unified cache + mem_handle)

> wherever a weight lives, it is materialized in the optimal memory layout for the processor that executes on it — per device, not globally. — Owner ruling, 2026-08-16 (layout follows residency)

> A tensor that never went through a model load has no owner, so it cannot be admitted at all. — SYCL Backend Memory Design (unified cache + mem_handle)

> Host-resident weights dispatch on CPU, not via GPU 'zero-copy' — and not via per-dispatch staging copies either. — SYCL Backend Memory Design (unified cache + mem_handle)

> Never store a raw void* from the cache. It becomes dangling the moment the cache evicts to host. Hold a mem_handle and resolve() at point of use. — SYCL Backend Memory Design (unified cache + mem_handle)

> Never add forced eviction / forced reap / zone-reset to reclaim memory that still has a live handle. A live allocation at cleanup means a leaked reference or stale owner — fix that, don't force the free. — SYCL Backend Memory Design (unified cache + mem_handle)

> Each region is sized at the caller's full requested capacity, not a fraction of it. — Epoch-refcounted transient zones (llama.cpp-2757 / iiff Option C)

## Contradictions

⚠️ **Contradiction**: The owner ruling behind llama.cpp-iiff — 'memory is freed only when references reach zero; the zones should not reset at all' — conflicts with the llama.cpp-37ba audit finding that blanket removal of bulk zone resets cannot be executed: for reset-only zones (VRAM scratch bump pool, host SCRATCH/STAGING, oneDNN scratch) the codebase's own comments state the bulk reset is the only reclaim path ('we don't actually free individual allocations'). The epoch-refcounted transient zones design is the reconciliation, keeping the bump allocator while adding per-region refcounting, and it explicitly notes that deleting the reset without a per-allocation release path would produce unbounded growth — the same failure mode (approached from the opposite direction) that the 'never add forced eviction' rule prevents.
⚠️ **Contradiction**: The deprecated-attribute advice on ensure_cached_alloc('use unified_alloc()') was explicitly judged wrong and removed in llama.cpp-og9dt: unified_alloc() creates no cache entry, ensure_cached_alloc() falls back to host memory when eviction is impossible (inverting 'refused under pressure' assertions), and allocate_slot() prefers the arena with no budget gate — so the test-only seam was retained by decision rather than the deprecation it once carried.
⚠️ **Contradiction**: The source text is truncated mid-sentence in its final section ('Epoch-refcounted transient zones', llama.cpp-2757 / iiff Option C), so the complete design of that section is not fully stated in the captured content.
