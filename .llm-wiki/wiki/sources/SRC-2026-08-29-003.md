# compute-runtime.md

## Summary

This machine-specific record documents a patched Intel compute-runtime (26.22, Battlemage/BMG-only) installed as the system-default Level Zero driver, the Level Zero loader cleanup, and — its core finding — the peer-to-peer (P2P) topology between the two discrete Arc cards. The patched libze_intel_gpu.so.1.15.38646 is built from branch llama/26.22-cross-device (based on upstream/releases/26.22) and carries a hung-i915 discovery fix, cross-device in-order dependency fixes, and the upstream PR 930 USM compression fix; it was configured with SUPPORT_BMG=TRUE and GEN/PLATFORM disabled because the installed IGC/ocloc cannot recognize 26.22's future Xe3p/NVLP built-ins. Stock 1.14.37020 and prior patched 26.09 files are preserved, with a documented symlink rollback procedure. Stale, unowned Level Zero loader/tracing/validation libraries were moved out of /usr/local/lib so new processes resolve the packaged loader. The Arc A580 described in the 2026-05-30 sections was replaced by an Arc Pro B70 on 2026-07-24.

⚠️ **Superseded on loader state (2026-09-02):** the claim below that the
patched 26.22 build is "the system-default Level Zero driver" was true only
through 2026-08-17. A one-way PPA upgrade on 2026-08-18 moved the loaded
driver to stock 26.31; the patched build remains on disk but unloaded. See
[SRC-2026-09-02-002](/sources/SRC-2026-09-02-002.md) and
[Intel compute-runtime](/entities/intel-compute-runtime.md). The P2P finding
below is unaffected — it is a PCI topology fact, independent of driver
version.

The central, re-verified (2026-07-31) result is that there is NO direct P2P between the two discrete cards (B70↔B50). This is a PCI topology restriction, not a property of either card: the two cards hang off different CPU root ports (00:06.0 vs 00:06.3) with no shared PCIe switch, so they meet only at the root complex — which is why swapping the B580 for the B70 in the same slot changed nothing. A 256 KiB direct device-to-device USM copy fails in both directions with a misleading UR_RESULT_ERROR_OUT_OF_DEVICE_MEMORY (error 39), can_access_peer correctly returns false in both directions, while ext_oneapi_enable_peer_access() wrongly returns OK.

Practical consequences: keep direct peer-copy and shared-context transfer paths disabled (host-bounce via ONEAPI_DEVICE_SELECTOR=level_zero:0,1 may continue), and keep GGML_SYCL_MOE_MULTI_GPU opt-in because the MoE multi-device path host-bounces expert data between two cards that cannot DMA to each other.

## Key Takeaways

- There is no direct P2P between the two discrete cards (B70↔B50); it is a PCI topology restriction, not a property of either card, since they hang off different CPU root ports and meet only at the root complex.
- Swapping the Arc A580 for the Arc Pro B70 (2026-07-24) in the same slot did not change the P2P verdict, confirming the restriction is topology-driven.
- Direct device-to-device USM copy fails in BOTH directions with a misleading UR_RESULT_ERROR_OUT_OF_DEVICE_MEMORY (error 39) despite 31.89 GiB free — a P2P refusal wearing a memory error's name.
- can_access_peer returns false in both directions and is the honest capability query; ext_oneapi_enable_peer_access() wrongly returns OK on hardware with no P2P, so it is NOT a capability check.
- Keep direct peer-copy and shared-context transfer paths disabled; host-bounce validation via ONEAPI_DEVICE_SELECTOR=level_zero:0,1 may continue.
- GGML_SYCL_MOE_MULTI_GPU must stay opt-in because the MoE multi-device path host-bounces expert data between cards that cannot DMA to each other (an earlier two-GPU run halved throughput, 32.11 → 15.81 tok/s).
- The patched 26.22/BMG-only compute-runtime is the system default, with stock 1.14.37020 and prior 26.09 patched files preserved and a documented symlink rollback; stale /usr/local/lib Level Zero libraries were quarantined to fix loader resolution.
- The single-context multi-GPU Level Zero variant was deliberately not re-run because it is the configuration recorded as triggering DEVICE_LOST on compute-runtime 26.x; the verdict rests on the device-level can_access_peer query and kernel refusal.
